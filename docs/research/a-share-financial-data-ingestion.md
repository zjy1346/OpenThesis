# A 股财报高稳定性结构化获取与识别方案调研

调研日期：2026-08-10  
范围：沪深北上市公司年报、半年报、一季报、三季报；重点关注三大财务报表、关键财务指标、修订版本和可审计证据。  
方法：优先查阅监管机构、交易所、项目官方文档、官方源码与许可证。本文不是法律意见；上线前仍需逐项确认数据服务协议和网站自动化访问条款。

## 结论

市场上已经存在成熟的**组成部件**，但没有找到同时满足下列全部条件的一站式方案：

- 官方支持且覆盖全 A 股和所有季度；
- 免费、无 Key、允许开源软件直接集成和再分发；
- 输出完整三表及叙述性财报内容；
- 能处理更正、合并/母公司、累计/单季口径；
- 每个数值都能回溯至原始披露位置；
- 对不同版式、扫描件仍能保持接近数据库级的准确性。

因此不应重新发明 OCR 或 XBRL 解析器。推荐采用成熟工具，独创的是一层“**官方披露优先、结构化数据优先、多源核验、会计规则校验、证据可追溯、失败关闭**”的编排与质量系统：

1. 官方公告/XBRL 是事实底稿和最高优先级来源。
2. 能取得 XBRL 实例时，用 Arelle 解析和验证；不能取得时，优先使用有明确字段和报告口径的结构化数据服务。
3. 原生 PDF 先做坐标化文本/表格解析；只有扫描件或乱码文件才进入 OCR。
4. 第三方数据只作为结构化输入或交叉验证，不替代官方原件。
5. 数据未通过身份、期间、单位、报表勾稽和来源一致性检查时，不调用 AI。

这比“换一个更强的 PDF 解析库”稳定得多。截图中的失败更像是**报表语义与口径校验失败**，而非单纯 OCR 不准：即使每个字都识别正确，若混淆了累计数与单季数、合并报表与母公司报表、当期与上年同期、元与万元，也会得到严重错误的数据。

## 一、官方结构化披露：应作为长期主轴

### 1. 监管标准已经覆盖全部定期报告

证监会发布的现行金融行业标准 [JR/T 0021.8—2023《上市公司公告电子化规范 第 8 部分：定期报告》](https://www.csisc.cn/zbscbzw/c100185/202310/8c1b3b4c1cc64f049f0d289935ca444e/files/%E3%80%8A%E4%B8%8A%E5%B8%82%E5%85%AC%E5%8F%B8%E5%85%AC%E5%91%8A%E7%94%B5%E5%AD%90%E5%8C%96%E8%A7%84%E8%8C%83%20%E7%AC%AC8%E9%83%A8%E5%88%86%EF%BC%9A%E5%AE%9A%E6%9C%9F%E6%8A%A5%E5%91%8A%E3%80%8B%E5%8F%91%E5%B8%83%E7%A8%BF.pdf) 明确规定：

- `GB0101` 为年度报告全文；
- `GB0301` 为一季度报告全文；
- `GB0501` 为半年度报告全文；
- `GB0701` 为三季度报告全文；
- 分类标准由 XSD 和标签、参考、展示、计算、定义链接库构成；
- 财务部分引用企业会计准则通用分类标准中的同义会计元素；
- 货币、日期、百分比、每股数等拥有明确数据类型；存量使用 `instant`，流量使用 `duration`；
- XBRL 实例必须通过 Schema、元素类型和链接库规则验证；
- 最终使用者可从正式发布的实例文档获取机器可读数据；实例文件包含公司、报告类型、公告编号、披露日期等身份信息。

[证监会 2023 年第 56 号公告](https://www.csrc.gov.cn/csrc/c101954/c7439562/content.shtml) 说明该系列标准自 2023-10-23 起实施，目标之一是提高披露的规范性、准确性、统一性和及时性。上交所也说明其已将 XBRL 用于上市公司定期报告，并实现了全部上市公司定期公告的全文 XBRL 信息披露；其分类标准曾通过 XBRL International 的 Approved 认证（[上交所与 XBRL](https://www.sse.com.cn/services/information/xbrl/ssexbrl/)、[上交所分类标准](https://www.sse.com.cn/services/information/xbrl/classification/)）。

### 2. 成熟解析器：Arelle

[Arelle](https://arelle.org/arelle/) 是成熟的开源 XBRL 平台，提供 GUI、CLI、Python API 和 Web Service API，支持 XBRL 2.1、Dimensions、Inline XBRL、Taxonomy Package 等，并获得 XBRL International 验证处理器认证。其 [GitHub 项目](https://github.com/Arelle/Arelle) 和 [发行说明](https://arelle.org/arelle/pub/) 表明使用 Apache License 2.0，适合 Windows/macOS 的本地集成。

推荐方式：

- 不自行写通用 XBRL 解析器；把 Arelle 作为隔离的解析/验证适配器。
- 固定并缓存每个版本的证监会/交易所分类标准包，禁止运行时悄悄切换 taxonomy。
- 不得把上交所公开页面中较早的 2005 draft 分类标准直接用于当前财报；只有实例实际引用且版本匹配的 taxonomy 才能进入生产解析。
- 将每个 fact 保存为：QName、中文标签、值、unit、decimals、context、instant/start/end、维度、来源实例文件、Arelle 验证结果。
- 映射到 OpenThesis 统一概念时保留原始 QName，映射表要版本化，不能只保存一个扁平数值。

### 3. 现实限制

标准证明了 XBRL 披露体系和实例格式是成熟的，但本次查阅的公开资料中，没有找到一个对普通桌面应用承诺 SLA、覆盖三家交易所、可匿名批量下载当前全部 XBRL 实例的稳定公开 API 文档：

- [上交所当前定期报告入口](https://www.sse.com.cn/disclosure/listedinfo/regular/) 可筛选年报、一季报、半年报、三季报；其[经营业绩概览](https://www.sse.com.cn/disclosure/listedinfo/listedcompanies/)说明展示数据源自公司提交的 XBRL 文件，同时明确最终应以 PDF 公告为准。
- 深交所[上市公司定期报告制作系统业务指南](https://docs.static.szse.cn/www/disclosure/notice/W020230804632650900092.pdf)要求通过制作系统生成并上传数据文件，说明监管端存在结构化报送流程；但公开可检索的深交所说明仅明确旧 XBRL 平台曾提供 2004—2008 年全部定期报告实例下载（[深交所历史公告](https://www.szse.cn/aboutus/trends/news/t20090213_517801.html)），不能据此推断当前普通用户拥有稳定的全量实例下载 API。
- 巨潮资讯是深交所法定信息披露平台，提供[沪深公告检索](https://www.cninfo.com.cn/new/commonUrl/pageOfSearch?checkedCategory=category_bndbg_szsh&url=disclosure%2Flist%2Fsearch)及“主要指标/财务报表”，但网站同时声明不保证数据绝对准确和完整（[巨潮公司披露页示例](https://www.cninfo.com.cn/new/disclosure/stock?orgId=gssz0000031&stockCode=000031)）。其网页法律声明允许非商业浏览和下载，商业使用或转售需要书面许可；正式数据产品/API 应通过[深证信数据服务平台](https://webapi.cninfo.com.cn/)咨询授权，公开页面未给出统一价格。

交易所和巨潮网页前端使用的 JSON 请求不是公开 API 契约，也没有对第三方应用承诺兼容性或 SLA，不能把逆向得到的内部端点当作长期架构。因此建议先做一个小规模“官方 XBRL 可获得性验证”项目，而不是直接把未文档化的网页内部接口写成唯一生产依赖。若交易所或深证信数据服务能提供正式数据接口/授权，应优先采用正式接口；否则仍需保留 PDF 与第三方结构化数据通路。

### Tushare Pro

Tushare 的官方文档提供了可直接映射到统一财务模型的成熟接口：

- [利润表 `income`](https://tushare.pro/document/2?doc_id=33)：包含 `period`、`report_type`、`comp_type`、`end_type` 和 `update_flag`；文档明确区分合并报表、单季合并、调整单季、调整前后及母公司报表。
- [资产负债表 `balancesheet`](https://tushare.pro/document/2?doc_id=36)：提供完整资产、负债、权益字段和报告期/报表类型。
- [现金流量表 `cashflow`](https://tushare.pro/document/2?doc_id=44)：提供报告期、报表类型及经营、投资、筹资现金流字段。
- [财务指标 `fina_indicator`](https://tushare.pro/document/2?doc_id=79)：报告期可为各季度期末，单股历史接口需至少 2000 积分，季度全市场 VIP 需 5000 积分。

Tushare 是目前最适合快速提高稳定性的成熟结构化方案，但不能成为 OpenThesis 的无条件默认依赖。[Tushare 数据服务协议](https://tushare.pro/document/1?doc_id=405) 对付费服务授予个人、不可转让、非商业用途许可，要求用户保护 Token，并明确平台不保证数据绝对准确、完整和及时。合理集成方式是“用户自行选择并配置 Token，数据只存其本机，OpenThesis 不提供或转售数据”。若未来项目或服务商业化，应另谈商业授权。

### BaoStock

[BaoStock 的 PyPI 官方项目](https://pypi.org/project/baostock/) 是中国证券数据 Python 客户端，元数据标注 BSD License，但开发状态为 Alpha。它适合无 Key 环境下核对 ROE、利润、现金流等季频指标。客户端许可证只约束软件代码，不自动授予服务端数据的再分发权；完整报表字段、银行/保险/证券口径、修订数据和最新季度及时性也需通过长期回归语料实测。因此应定位为第二来源，不应在其单独返回一致时跳过官方原件校验。

### AKShare

[AKShare 官方 A 股文档](https://akshare.akfamily.xyz/data/stock/stock.html) 包含：

- 新浪三大报表历史数据 `stock_financial_report_sina`，示例数据包含 3/31、6/30、9/30、12/31；
- 东方财富按报告期获取利润表等接口；
- 巨潮公告查询接口，可按年报、半年报、一季报、三季报筛选；
- 财报预约披露日期。

AKShare 源码使用 [MIT License](https://github.com/akfamily/akshare/blob/main/LICENSE)，但其 [项目声明](https://github.com/akfamily/akshare) 明确说数据仅供学术研究、存在数据风险，并且一些接口可能因不可控因素被移除。它包装的是新浪、东方财富、巨潮网页接口，而非对 OpenThesis 提供 SLA 的数据合同。因此适合作为可替换的第三来源和测试工具，不适合作为单点生产依赖。

## 三、PDF 与 OCR：采用成熟工具，但不能让工具直接决定财务事实

### 原生 PDF 优先

大部分官方财报是机器生成 PDF。应先检查页面是否有可靠文字层、字体映射和字符坐标，再决定是否 OCR。

[pdfplumber](https://github.com/jsvine/pdfplumber) 提供字符、线条、矩形、表格边界和可视化调试；官方文档明确称其更适合机器生成而非扫描 PDF，并支持按线条或文字对齐推断表格。其许可证为 [MIT](https://github.com/jsvine/pdfplumber/blob/stable/LICENSE.txt)。适合用来保存“页码 + 单元格边界 + 原文”的可审计证据。

不建议仅依赖通用 `extract_table()` 输出二维数组。稳健解析必须先用标题锚点定位“合并资产负债表/合并利润表/合并现金流量表”，识别单位、币种、报告期间和列标题，再以会计科目别名映射行；跨页续表必须保留表头状态。

### PaddleOCR / PP-StructureV3

[PP-StructureV3](https://paddlepaddle.github.io/PaddleOCR/main/version3.x/pipeline_usage/PP-StructureV3.html) 支持 PDF/图片的版面检测、OCR、表格识别、阅读顺序恢复，并能输出 JSON、Markdown、HTML/XLSX 表格及识别置信度。它允许对表格、文字、版面等子模块做针对性微调。PaddleOCR 项目的 [pyproject.toml](https://github.com/PaddlePaddle/PaddleOCR/blob/main/pyproject.toml) 标注 Apache License 2.0。

推荐将它作为默认 OCR 兜底，但只处理以下文件：

- 页面无有效文字层；
- 字体编码导致抽取文本大面积乱码；
- 财务表格是嵌入图片；
- 原生表格解析无法形成足够行列结构。

OCR 数字必须逐字符保存置信度，任何包含低置信度数字、负号、括号、小数点或单位的核心事实都必须降级或人工/第二来源复核。

### MinerU

[MinerU](https://github.com/opendatalab/MinerU) 能将 PDF/图片转换为 Markdown/JSON，支持复杂版面、表格 HTML、跨页表格合并、扫描件 OCR、可视化调试和 CPU/GPU/MPS。其 [输出格式文档](https://opendatalab.github.io/MinerU/reference/output_files/) 提供 page、bbox、table、text 等中间结构，适合疑难文档插件。

但它不应成为默认 Windows 包的唯一解析引擎：模型和后端较重，输出结构在不同后端/版本间有不兼容变化，且官方也承认复杂布局和扫描场景可能不符合预期。其 2026 年许可证已改为 [MinerU Open Source License](https://github.com/opendatalab/MinerU/blob/master/LICENSE.md)，以 Apache 2.0 为基础但增加大型商业用户门槛和在线服务署名义务。建议作为可选高精度插件，固定版本并在界面/文档满足署名要求。

## 四、推荐的分层架构

### L0：公告清单与不可变原件库

每次研究先建立 `FilingManifest`，至少包含：

- 证券代码、交易所、公司法定名称；
- 公告类别码/报告类型、报告期、披露时间；
- 原始标题、官方 URL、来源平台；
- 是否更正/修订/取消、被替代公告 ID；
- PDF/XBRL 文件 SHA-256、字节数、抓取时间、HTTP 元信息。

只按公告类别和期间选择文件，不靠标题模糊匹配。遇到更正公告时保留旧版本，但只让最新有效版本进入主分析；历史版本仍用于审计。

### L1：官方 XBRL 解析

若公告能取得 XBRL 实例：

1. 用 Arelle 加载固定版本 taxonomy；
2. 执行 Schema、类型、计算链接库等验证；
3. 保存原始 fact 上下文；
4. 映射到统一会计概念；
5. 不将 Arelle “验证通过”等同于经济事实一定正确，仍运行 L4 会计检查。

### L2：结构化数据适配器

建立可插拔的 `StructuredFinancialProvider`：

- `tushare`：推荐的用户自配主适配器；
- `baostock`：免费关键指标复核；
- `akshare`：开发和第三来源；
- 将来可接入获得正式授权的深证信、交易所或其他商业数据库。

所有适配器输出相同的 `FinancialFact`，但必须保留 provider、源字段、请求报告期、报表类型、修订状态和抓取时间，不能只返回 `year/value`。

### L3：官方 PDF 证据解析

处理顺序固定为：

1. PDF 完整性与签名/哈希检查；
2. 原生文字层质量探测；
3. 财务报表标题、单位、币种、合并/母公司、期间列识别；
4. pdfplumber 坐标化表格解析；
5. 原生解析失败才调用 PaddleOCR；
6. 极复杂文件才调用可选 MinerU；
7. 将每个数值绑定到 `page + bbox + raw_text + parser_version`。

### L4：统一语义、期间与会计校验

这是应由 OpenThesis 独创并形成核心竞争力的一层。

**身份校验**

- 文档中的证券代码、公司名称必须与研究对象一致；
- 报告期和报告类型必须与公告清单一致；
- 合并报表与母公司报表不能混用；
- 一般工商业、银行、保险、证券使用不同 schema。

**期间校验**

- 资产负债表是期末时点值；利润表/现金流量表是期间累计值；
- Q1、H1、Q3 的累计值只与上年同期间比较；
- 单季数只能由明确的单季报表取得，或用累计值确定性相减得到并标记为 derived；
- 年报不得与 Q1/H1/Q3 填入同一个年度槽位；
- 不允许把财报发布时间当成报告期末。

**单位校验**

- 单位必须来自表头或 XBRL `unitRef`，支持元、千元、万元、百万元；
- 百分比、每股数、股数和货币不可互转；
- 括号负数、破折号空值和“0”必须区别保存。

**会计勾稽**

- `资产总计 ≈ 负债合计 + 所有者权益合计`；
- 现金及现金等价物期末余额与期初余额、净增加额、汇率影响相协调；
- 报表小计与子项在允许容差内一致；
- 利润表营业利润、利润总额、净利润链条做方向和数量级检查；
- 当 XBRL calculation linkbase 可用时，优先采用其关系，不硬编码所有行业公式。

**多源一致性**

- 核心事实至少需要官方 XBRL、官方 PDF、结构化服务三者中的两个一致，或一个官方结构化事实加完整验证链；
- 差异比较同时考虑修订版本、合并/母公司、累计/单季、单位和舍入；
- 不应使用简单的“多数票”：官方最新更正文件优先于多个滞后的镜像数据源。

### L5：证据账本与 AI 闸门

每个进入 AI 的事实必须能返回：

- 标准概念和规范化值；
- 原始值、单位、期间和报表口径；
- 官方 URL、文件哈希、公告 ID；
- XBRL QName/context，或 PDF 页码/bbox/原文；
- 解析器、映射表和验证规则版本；
- 多源比对结果、派生公式和置信等级。

闸门状态建议使用明确的枚举，而非一个笼统错误：

- `DISCOVERY_FAILED`：未找到应存在的官方公告；
- `DOCUMENT_UNAVAILABLE`：公告存在但文件无法下载；
- `UNSUPPORTED_FORMAT`：文件完整但当前解析器不支持；
- `IDENTITY_MISMATCH`：公司/期间/类别不一致；
- `EXTRACTION_INCOMPLETE`：核心三表字段不足；
- `ACCOUNTING_RECONCILIATION_FAILED`：会计勾稽失败；
- `SOURCE_CONFLICT`：多个来源在统一口径后仍冲突；
- `READY_WITH_WARNINGS`：非核心字段缺失，但核心数据可信；
- `READY`：核心事实通过验证。

只有最后两个状态可以调用 AI；`READY_WITH_WARNINGS` 必须把缺口传给 Agent，不得把缺失值伪装为 0。

## 五、应淘汰的方案

1. **淘汰“PDF 全文正则 + 中文科目名称直接取邻近数字”作为主解析器。** 它无法可靠识别跨页、单位、列标题和报表口径。
2. **淘汰“所有 PDF 无条件 OCR”。** OCR 会破坏原生 PDF 已有的精确字符和坐标，并引入数字、负号、小数点错误。
3. **淘汰“让大模型从整份财报自由提取核心数字”。** LLM 可做叙述内容归纳，不能成为确定性财务事实的唯一来源。
4. **淘汰“单一 AKShare/新浪/东方财富内部接口”。** 接口没有针对 OpenThesis 的稳定契约，且 AKShare 官方已提示接口可能移除。
5. **淘汰“按年份覆盖数据”。** 必须以 `entity + statement + fiscal_period + period_start/end + consolidated_scope + currency + unit + revision` 为主键。
6. **淘汰“失败后继续把部分错误事实送给 AI”。** 对投资研究而言，明确停止并说明故障层级优于生成一份看似完整但口径错误的报告。
7. **不建议把 Tushare 数据或 Token 打包进开源发行版。** 其个人非商业许可和账号不可转让限制与内置再分发模式不兼容。

## 六、落地顺序与验收标准

### 第一阶段：结构化输入替代 PDF 猜测

- 增加 provider 插件层和用户自配 Tushare Token；
- 保存官方公告 PDF 作为证据，不再让现有 PDF 正则成为首选数字源；
- 实现严格期间、单位、合并口径和修订去重；
- BaoStock/AKShare 只做第二来源；
- 界面展示明确失败分类。

这一阶段最快解决“官方文件已下载但关键字段一致性校验失败”的用户痛点。

### 第二阶段：官方 XBRL 试点

- 分别选上交所、深交所、北交所样本验证实例文档取得方式；
- 集成 Arelle，固定 taxonomy 和映射版本；
- 先覆盖一般工商业，再覆盖银行、保险、证券；
- 若无法取得正式、稳定、合规的公开实例下载渠道，则保留为“可获得时优先”，不依赖逆向网页端点。

### 第三阶段：高稳定 PDF 兜底

- 原生 PDF 使用 pdfplumber 坐标解析；
- 扫描/乱码使用 PP-StructureV3；
- MinerU 作为可选疑难文档插件；
- 建立真实财报黄金语料并持续回归。

### 建议验收指标

- 公告发现召回率：测试语料中年报/H1/Q1/Q3 不漏报，修订链正确；
- 报告身份错误：0；
- 年报与季度混写：0；累计与单季混写：0；合并与母公司混写：0；
- 核心事实（收入、净利润、资产、负债、权益、经营现金流）在黄金语料上的精确率达到约定阈值后才发布；
- 所有进入 AI 的核心事实具备可点击的官方证据定位；
- 任一解析器升级必须对全部黄金语料跑差异报告；
- 无法可靠解析时必须失败关闭，不得以 0、负数异常值或错误增长率继续研究。

黄金语料应覆盖：沪/深/北三所、主板/科创板/创业板、一般公司/银行/保险/证券、四类定期报告、更正报告、跨页表、无框线表、千元/万元单位、括号负数、扫描件、特殊字体、上市不足一年和会计政策追溯调整。

## 最终建议

OpenThesis 应采用“**成熟组件 + 自研可信数据层**”，而不是寻找一个神奇的 PDF 识别模型：

- XBRL：Arelle；
- 原生 PDF：pdfplumber 等坐标化解析；
- 扫描件：PaddleOCR/PP-StructureV3；
- 极复杂文档：可选 MinerU；
- 快速稳定结构化数据：用户自配 Tushare；
- 免费交叉验证：BaoStock/AKShare；
- OpenThesis 自研：公告版本链、统一 schema、期间语义、会计勾稽、多源裁决、证据账本和 AI 闸门。

该路线既能显著提高近期 A 股可用性，又避免锁定某个收费源或网页内部接口；核心 schema、证据模型和验证器可跨 Windows/macOS 复用，也为未来接入港股 XBRL、交易所正式接口或商业数据源留下稳定扩展点。
